# SpecTwin Design Implementation Plan

Generated by `plan-eng-review` on 2026-06-08.

## Recommendation
Ship the design refresh in two layers:

1. Build the shared UI foundation first.
2. Migrate screens onto that foundation in controlled slices.

Do not restyle every module by hand in one pass. That would touch too many files, duplicate constants, and make visual regressions hard to isolate.

## Step 0: Scope Challenge

### What already exists
- Font loading already exists in `StartScreen.py` and `SpectwinMain.py`, but each file owns its own registry call.
- A start screen exists and already loads logo textures.
- The main shell already has a left menu and content area.
- Module switching tests already verify all major module entrypoints can build without showing the viewport.
- A Windows GUI smoke test already drives navigation with `pywinauto`.
- Local item themes already exist for selected calibration points and periodic table element states.

### Scope reduction
The initial design plan could easily touch 10+ UI files. That is too broad for a safe first implementation.

Recommended first slice:

1. Add shared theme/tokens/helpers in `Source/UI/`.
2. Apply global theme and font registration in `StartScreen.py` and `SpectwinMain.py`.
3. Replace only the most visible local colors in `DigitalTwinUI.py`, `AutoFDMNESUI.py`, `CalibrationAppUI.py`, and `PeriodicTableDPG.py`.
4. Add tests proving the shared theme helpers create expected DPG items and module screens still build.

Leave full layout redesign of every data module to follow-up work.

## Architecture Review

### Issue A1: Theme logic must be centralized
Confidence: 9/10.

Current code hard-codes colors in multiple modules. If the refresh edits each module directly, the app will drift again.

Recommendation: create `Source/UI/theme.py` with:
- color token constants
- spacing constants
- `load_fonts()`
- `build_app_theme()`
- `build_plot_theme()`
- item theme helpers for primary, secondary, warning, success, error, selected, included, and excluded states

Framework fit: Dear PyGui supports themes as containers with components, colors, and styles. Themes can be bound globally, to containers, or to item types. Fonts can be loaded in a font registry and bound globally or to a specific item/container.

### Issue A2: Helpers should wrap patterns, not the whole UI
Confidence: 8/10.

Avoid creating a new abstraction layer that replaces Dear PyGui. This codebase is currently straightforward DPG calls. A heavy component framework would slow future contributors down.

Recommendation: create small helper functions only where duplication is real:
- `add_section_title(text, parent=None)`
- `add_status_text(default="", state="idle", parent=None, tag=None)`
- `bind_button_theme(item, variant)`
- `bind_plot_theme(item)`

Keep module layout code readable in the module files.

### Issue A3: Font plan needs graceful local fallback
Confidence: 8/10.

`DESIGN.md` recommends Source Sans 3 and IBM Plex Mono, but the repo currently contains only Verdana files. Do not introduce runtime network font loading in a desktop science app.

Recommendation:
- Implement `load_fonts()` to prefer local Source Sans 3 and IBM Plex Mono if present.
- Fall back to existing Verdana.
- Keep tests independent of optional font files.

## Code Quality Review

### Issue C1: Avoid magic RGB tuples after the theme module exists
Confidence: 9/10.

Current examples:
- `StartScreen.py` uses white background and gray text directly.
- `CalibrationAppUI.py` uses orange and green tuples directly.
- `PeriodicTableDPG.py` creates green and red button themes from local tuples.
- `AutoFDMNESUI.py` draws XES peaks in pure red.

Recommendation: after `Source/UI/theme.py` lands, new UI code should import named tokens instead of hard-coding colors. Existing hard-coded tuples can be replaced incrementally.

### Issue C2: Tags and registries are fragile
Confidence: 7/10.

The code already has careful duplicate-tag handling around `texture_reg`, plot handlers, and module reopening. Theme registries can create the same problem if they use fixed tags without idempotent checks.

Recommendation: make theme creation idempotent. Before creating shared theme/font registries, check `dpg.does_item_exist(tag)` or return cached IDs from module-level state.

### Issue C3: Start screen layout should not use spacer centering
Confidence: 8/10.

The start screen uses fixed spacer widths for centering. It works at the current viewport but will break if the window changes or assets are replaced.

Recommendation: in the implementation slice, convert it to grouped blocks with predictable dimensions and a theme-bound launch button. Do not over-engineer full responsiveness for the fixed desktop launcher.

## Performance Review

### Issue P1: Font atlas and texture work should stay one-time per context
Confidence: 7/10.

Dear PyGui fonts render through a font atlas. Re-registering fonts or repeatedly creating theme registries during module switches is unnecessary and can create UI instability.

Recommendation: theme/font setup should happen once per DPG context in the top-level screen builders. Module-specific item themes should be reused or created idempotently.

### Issue P2: Do not restyle plots on every data update
Confidence: 8/10.

Plots and draw layers update during simulation, optimization, peak picking, and data visualization. Rebinding themes during data updates would add churn where users need responsive plots.

Recommendation: bind plot themes at construction time. Update only plot data, draw layers, and status text during runtime actions.

## Failure Modes

| Failure | User impact | Plan coverage |
|---|---|---|
| Missing preferred font files | App fails at startup or silently looks wrong | Fallback test required |
| Duplicate DPG theme tags on module reopen | Navigation crashes or module fails to rebuild | Idempotency test required |
| Dark global theme makes file dialogs unreadable | Users cannot select files reliably | Manual GUI smoke and file dialog check required |
| Plot theme reduces axis/grid contrast | Users misread spectral data | Visual QA screenshot required |
| Pure color-only status remains in periodic table | Accessibility and meaning gap | Include/exclude summary or tooltip follow-up |

## NOT In Scope
- Full redesign of every data-processing module in the first slice. Too much surface area for one safe PR.
- Replacing Dear PyGui with another UI framework. The current app and tests are built around DPG.
- Shipping new font binaries unless licensing is confirmed.
- Changing simulation, FDMNES, xrt, data-processing, or optimization behavior.
- Adding light mode. `DESIGN.md` explicitly treats the dark workstation as the primary UI.

### Pass 1: Information Architecture

Implementation decision: do not let individual modules invent their own top-level page structure. Each migrated module should start with a compact module heading/status row, then use tabs or panels below it.

### Pass 2: Interaction State Coverage

Score after review: 6/10 -> 8/10 with this addendum.

Add this state table to implementation acceptance criteria:

| Area | Idle | Loading/Running | Empty | Success | Warning | Error |
|---|---|---|---|---|---|---|
| Start screen | Launch button ready | Launch disabled or subtle busy state | Missing logo fallback | Main app opens | Optional dependency warning | Startup failure message |
| Main shell | Welcome/module selected | Module switching in progress if needed | No module content | Module loaded | Module unavailable | Module build failed |
| Digital Twin | No lines selected | Simulation/optimization running | No results yet | Results and convergence visible | Too many targets selected | Invalid HKL, no crystal, failed run |
| AutoFDMNES | No elements selected | FDMNES running | No CIF/results/peaks | Peaks/table populated | Peak pick mode active, missing selection | Simulation failed, parse failed |
| Data modules | No file selected | Reading/processing | No data displayed | Plot/table rendered | Partial file/filter mismatch | File read or processing error |
| File dialogs | Dialog ready | N/A | No matching files | File selected | Unsupported extension | Dialog unreadable or missing |

Implementation decision: create a shared status helper that supports `idle`, `running`, `empty`, `success`, `warning`, and `error`. Plain `dpg.add_text("Error...")` should be treated as legacy UI after the first slice.

### Pass 3: User Journey And Emotional Arc

Score after review: 7/10 -> 8/10 with this addendum.

```text
STEP | USER DOES                         | USER SHOULD FEEL                  | DESIGN SUPPORT
-----|-----------------------------------|-----------------------------------|----------------
1    | Opens SpecTwin                    | "This is serious lab software"    | Dark instrument-grade launcher, restrained logo use
2    | Enters main shell                 | "I know where to start"           | Left rail, module title, clear welcome state
3    | Chooses a workflow                | "This has a process"              | Tabs/step labels and status row
4    | Enters parameters or files        | "The app understands my data"     | Dense labels, aligned numeric fields, helper text
5    | Runs simulation/processing        | "Something is happening safely"   | Running status, disabled duplicate actions where needed
6    | Inspects plot/table output        | "I can trust these numbers"       | Plot contrast, monospace numeric values, clear legends
7    | Exports or routes results         | "I can continue my research"      | Consistent export/send actions and success state
```

Implementation decision: visual polish should prioritize trust during long analysis sessions, not a flashy first impression.

### Pass 4: AI Slop Risk

Score after review: 8/10.

The current design direction avoids the major AI slop traps: no purple gradients, no marketing hero, no 3-card feature grid, no bubbly radius.

Remaining risk: a generic dark dashboard look. Avoid this by using scientific UI signals:
- plot grid and axis contrast as a first-class design object
- monospace numeric values for scientific outputs
- workflow state tied to spectroscopy actions, not generic "cards"
- amber only for measurement attention, not random decoration
- institutional logos kept quiet and secondary

Implementation decision: do not make the start screen a dramatic hero page. It is an entry hatch into a workstation.

### Pass 5: Design System Alignment

Score after review: 8/10 -> 9/10 with this addendum.

Add these concrete alignment rules:
- Active module, active tab, primary action, selected peak, and selected workflow step must all use spectral cyan or a cyan outline.
- Warning, peak-pick attention, and measurement annotations use amber.
- Success/completed states use green.
- Errors use red, but failed scientific computation messages should include text and context, not just red color.
- Tables and numeric output should prefer mono styling once font support exists.
- Child windows used as layout panels should have visible surface hierarchy unless they are pure plot canvases.

### Pass 6: Responsive And Accessibility

Score after review: 5/10 -> 8/10 with this addendum.

SpecTwin is a Windows desktop application, so mobile responsiveness is not the target. Accessibility still matters.

Acceptance criteria:
- Minimum button height: 32 px for dense controls, 40 px for primary launcher/run actions.
- Color is never the only signal for include/exclude, selected/error, or running/done.
- Text contrast should target WCAG AA where Dear PyGui permits it.
- Long file paths and long material/formula names must wrap or truncate without shifting core controls.
- File dialogs must remain readable under the global dark theme.
- Keyboard navigation should remain functional for existing Dear PyGui controls. Do not replace native controls with custom draw-only controls in the first slice.
- Modal buttons should be ordered consistently: confirm action first, cancel/close second.

### Pass 7: Unresolved Design Decisions

Resolved for first implementation:
- Use the dark graphite workstation as the primary theme.
- Keep Verdana fallback until preferred font files are added and licensing is confirmed.
- Use small helpers, not a full component framework.
- Do not redesign every module layout in the first slice.
